# Repository design and modularity practices

## Preserve architecture while reducing implementation complexity

Use a modular core plus the isolation boundaries already defined in LLD01. A package is a unit of responsibility/testing/dependency, not automatically another service. Separate deployables where credentials, trust or failure domains require them: untrusted runtime, inference gateway/bridge, identity, data gateway, host help/static and recovery authority. Do not collapse runtime and data identity for convenience or create a microservice for every class.

Planned layout: apps/web; services/{edge,identity,core,runtime,inference,data,control,jobs,simulators,telemetry}; host/{help,static,inference-bridge,recovery-control} packages; packages/contracts/{python,typescript}; packages/domain; packages/policy-input; packages/rendering; config/demo; deploy/k8s/{base,overlays}; tests/{contract,unit,integration,race,e2e,network,recovery,evaluation}; tools. These are future implementation paths, not application files generated by this task. Use underscore import/package names even where logical directory names use hyphens.

Python members use src layout, typed public ports and explicit package exports. Domain logic depends on immutable values/protocols, not FastAPI/SQLAlchemy/HTTP clients. Application handlers coordinate use cases; adapters bind HTTP/DB/model/clock implementations at a composition root. Keep configuration/logging/connection setup out of import-time side effects. Avoid a generic service locator or “utils” module that owns unrelated authority.

Dependency direction: UI→BFF→core→named data/PDP/inference/simulator ports; runtime→broker only; data gateway→business PostgreSQL and live journal head; identity→own store/provider; host help→fresh identity plus own spool. Shared contract packages carry shapes, not DB credentials or policy bypass functions. Verify these boundaries through package declarations/import rules and deployed network tests. A development uv workspace is not runtime privilege isolation; images install only the selected service and its runtime dependencies.

## Python/API/data practices

Keep routers thin and operation-specific; FastAPI dependencies construct verified current context and scoped resources, not caller-declared authority. Pydantic models reject unknown keys and inappropriate coercion; retain LLD JSON Schema as the reviewed design source and prove generated/handwritten adapters agree. HTTP input DTO, domain value and persistence row have different jobs. Do not serialize an ORM object directly as a permitted view. [FastAPI modules/routers](https://fastapi.tiangolo.com/tutorial/bigger-applications/), [Pydantic model rules](https://docs.pydantic.dev/latest/concepts/models/).

The gateway alone owns business DB engines/sessions. Use SQLAlchemy typed queries and explicit transaction scopes with Psycopg/PostgreSQL integration; keep final LLD lock order/guard checks/audit/outbox atomicity visible in code. No ORM convenience method substitutes for consent/assignment/missing-row race control. If using AsyncSession, one per request/task/unit of work, never shared concurrently. CPU/FS blocking work uses a bounded executor; model calls do not hold DB locks. External sends are outside DB transactions and reconcile by stable identity. [SQLAlchemy asyncio guidance](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).

Alembic migrations have stable names/digests, explicit SQL privileges/RLS/functions/constraints, expansion/backfill/contract plan and tested upgrade/compatibility. Autogeneration is a draft for review; it does not prove correct grants, data migration or rollback. Identity/simulator/help stores have separate migration/custody boundaries. Use real PostgreSQL for locks, RLS, constraints and recovery tests; SQLite is only the explicitly selected help-spool binding. [Alembic autogeneration limitations](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).

## React/TypeScript practices

Organize by actor capability—intake, workforce, plan/consent, referral, governance—behind shared accessible primitives and typed API clients. Keep remote server state separate from transient form/display state. Server remains authoritative for role, ownership, assurance and effect status; UI controls improve usability, never grant permission. Avoid giant universal chat/role components, duplicate business rules, untyped API casts and prop chains carrying broad actor context.

Use TypeScript strict mode with noUncheckedIndexedAccess and exactOptionalPropertyTypes; model finite states as discriminated unions and exhaustiveness checks. Keep bigint revisions as canonical strings. Explicit pending/unknown/unconnected states are product behavior, not generic green success toast. Controlled forms preserve unsent input across reauthentication without storing private content in browser persistent caches. Effects clean up subscriptions and discard stale revisions/epochs; do not use an effect to trigger an irreversible duplicate send.

Use reviewed EN/FR semantic message keys, accessible labels/focus/errors/live regions and plain source/unknown/conflict display. Review screens show exact diff/recipient/fields/purpose/expiry and let a human edit/reject. Shared test fixtures exercise authorization on direct API calls too. Through IMP-10, run automated keyboard, focus, semantic accessibility, EN/FR and axe checks; user-level component tests should follow actual interactions. Record human screen-reader and visual review as deferred to post-IMP-10 GitHub issue follow-up sessions, not as an automated pass. [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html), [React Testing Library](https://testing-library.com/docs/react-testing-library/intro/).

## Contract and ownership discipline

All 206 LLD operations have an allocated completion stage in the machine plan; allocation is planning only. The 391 LLD type definitions include internal gateway wrappers and release metadata, not 391 user features. Implement only the stage's declared behavior; do not build success-returning shells for the entire inventory. Contract code generation is reproducible/pinned and reviewed as a coordinated change. Preserve duplicate-key rejection, decimal overflow, unknown fields, exact model selection and semantic checks—not only ordinary JSON parsing or static typing.

Do not turn current design ambiguities into silent implementation choices. File-specific/operation-specific findings are documented as an LLD amendment with compatibility/tests and actual human decision where authority changes. Keep domain, security, actor usability and operations decisions connected in a single reviewable slice.
