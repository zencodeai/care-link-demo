# Physical storage, constraints and transactions

## Storage contract

PostgreSQL business/control/audit share one transaction boundary. Identity uses a separate database and DB role; simulator uses its own synthetic store; host help uses its own transactional spool (proposed SQLite with FULL synchronous durability and verified host filesystem behavior); host journal files are separately credentialled. They do not share a distributed transaction.

Common business columns `B`: `id uuid PK`, `environment text CHECK='demo'`, `population text CHECK='synthetic'`, `revision bigint CHECK>=0`, `created_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL`. Append records use creation time plus immutable sequence, no editable revision. Access metadata columns are explicitly classified `access_metadata`, never labelled synthetic merely because a table has a business parent. UUID references below are NOT NULL unless `?`; concrete same-database FKs are enumerated in the physical dictionary with `ON DELETE RESTRICT`; polymorphic aggregate/source/actor/content references are typed repository-validated references, not fictitious generic FKs. Cross-DB IDs are verified opaque references, not pretend FKs. Text bounds mirror wire definitions and are checked in commands; enum columns have CHECK constraints. Byte digests are exactly 32 bytes. UTC instants and bigint sequence overflow fail rather than wrap.

## Roles, projection and migration

DB owners are offline NOLOGIN roles. Runtime login roles are nonowner, NOSUPERUSER, NOBYPASSRLS with no DDL/TRUNCATE or arbitrary function execution. Separate gateway command/projection, audit append/read, lifecycle purge and backup roles. Enable and FORCE RLS on protected tables as defense in depth; RLS cannot protect against owner/superuser/root and is not a replacement for named projection methods. If privileged append functions are used, qualify objects, fix trusted search_path and revoke PUBLIC EXECUTE in the creation transaction; grant only exact gateway calls. No browser/user-selected session variable is an authorization source. Gateway constructs transaction-local verified context; RLS filters session/purpose and command code filters fields. A compromised gateway remains a residual within its narrow DB grants. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) documents bypass/whole-table limitations; deployment pins and privilege probes must verify the chosen version.

Migrations are ordered immutable files with digest/version in release manifest. Expand nullable/additive structures, dual-read only under explicit compatible DTO version, backfill bounded idempotent batches, validate constraints, switch readers, then contract only after old version is fenced and backup compatibility assessed. A failed or unknown migration leaves readiness false. Destructive rollback restores into quarantine and follows current-authority promotion; no live database rewind that resurrects grants. Fixtures seed only named demo resources with environment checks; account provisioning and journal are not reset with personas.

## Transaction algorithm and linearization

Initial concurrency favors correctness over throughput. READ COMMITTED uses locked current rows, not a stale snapshot. Prepare expensive validation/PDP context outside transaction; final transaction locks in this exact order: global control guard → principal guards sorted UUID → subject guards sorted → session guards sorted → service guards sorted → domain rows sorted → operation/outbox rows → audit head. Take `FOR UPDATE`; all modifying paths and restrictive controls use the same guards. A nonexisting grant is serialized through its preexisting subject guard. New resource creates parent/guard atomically; no opportunistic invented subject when a lookup misses. [PostgreSQL locking](https://www.postgresql.org/docs/18/explicit-locking.html) informs the row-lock behavior; a missing-row SELECT is not a lock on future grants.

Final boundary: fetch fresh host restriction barrier while holding global control guard, require DB applied barrier and serving generation current; verify current identity evidence/local role revision, ownership/assignment, consent interval/scope, directory suspension/freshness, task lease/control epoch, payload/review digest, PDP epoch/deadline and all obligations. Re-read current metadata after acquiring locks; changed inputs cause rollback/re-evaluation (max 2 proposed attempts within original deadline), not permit reuse. Audit append, domain change, operation outcome and outbox intent commit in one transaction. No protected result/effect before commit. Transaction/lock timeout is bounded by 1000ms authorization budget; on deadlock/serialization error retry only same logical key under original deadline. Do not call model, receiver or unbounded network while holding locks.

Protected read: metadata-only lookup→PDP→final guards/recheck→create minimized projection and canonical disclosure audit→commit→release bytes. Audit failure releases no private bytes. Reads may serialize under the demo global guard; measure cost. Stable operation ID separates canonical decision from linked attempts/receipts. Lost commit acknowledgement queries operation identity and reauthorizes result access. Denial audit uses a separate transaction when the attempted transition rolled back; audit-down cannot produce a successful protected response.

## Host restriction journal publication

Recovery-critical deny/revoke/delete/hold/control changes acquire control guard, append a signed hash-chained INTENT to host journal with command ID and expected head, fsync durable bytes+head metadata, then update domain/control state, applied barrier, canonical audit and recovery.command in DB and commit. INTENT advances a separate restrictive barrier; terminal ACK advances journal tip only. Every protected authorization requires fresh barrier equality/applied coverage. Journal-success/DB-failure therefore blocks stale permission until reconcile. DB commit unknown is resolved from command ID; do not append a different restriction blindly. Reconciliation applies idempotently and records terminal evidence. Restrictive unresolved intent remains denied; a relaxation/hold release intent never grants permission on replay and requires verified DB commit/appropriate authorization. Exact intent types and recovery cutover appear in chapter12. No DB/file/network atomicity is asserted.

## Child operation and inference persistence

`durable.operation` also stores root_operation_id/parent_operation_id nullable UUID references, phase enum enqueue/authorization/attempt/receipt/disclosure/control and contract_version text. Canonical audit uniqueness applies to each child logical operation, not all phases of one root. `tasks.observation` stores id UUID PK, task_id/step_id/invocation_id UUID, task_revision/fence BIGINT, outcome closed ObservationOutcome DTO, source references, digest and created_at; UNIQUE(invocation_id). `tasks.inference_job` and `tasks.compute_slot` use the exact fields/states in chapter07; slot ID is unique, active job/slot association unique, no freeing on caller timeout. `care.post_crisis_event` stores id/session/source event UUIDs, attributed actor reference, occurred_at/created_at and revision, never inferred by background silence. `access.scoped_grant` stores exact grantee/purpose/resource/fields, approval and expiry; it cannot grant subject consent or reviewer independence.

## Normative physical dictionary and evidence records

[storage-model.json](storage-model.json) enumerates native column types/nullability, PKs, uniqueness, concrete FK targets, index prefixes, checks and classifications. The table above explains ownership/behavior; the machine dictionary makes physical representations explicit. It is not executable DDL or a tested migration. PostgreSQL JSONB columns bind to closed DTO schemas, not arbitrary authority objects. JSONB source/aggregate/actor references resolve type, owner, current revision and permitted scope through named repositories; no implied cross-table polymorphic FK. Domain state/check enums remain the corresponding closed DTO/state-machine sets.

Manual drafts have nullable task_id; every referral has an exact draft_id and optional review_id FK, independent of AI availability. Separate care.inbox_message stores stable effect-key/recipient/followup/template/content/lifecycle, without reopening ended sessions. Follow-up pending anchor uses null post_crisis_event_id/due_at/expires_at and cannot send; bind-anchor transaction sets all three with separate current contact consent. Tombstone and promotion/review records are listed explicitly; none can replace live journal/gate authority. Host SQLite spool uses canonical TEXT identifiers/times and BLOB digests, checked integer booleans, foreign_keys=ON, synchronous=FULL and WAL with verified fsync behavior. Its local transaction never includes the business DB.

SQLite foreign-key enforcement must be enabled and verified per connection; WAL is local-host storage and its durability still depends on the selected VFS/filesystem. Verify returned pragma values and pin a supported fixed SQLite version before admission. See [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html), [synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous) and [WAL behavior](https://www.sqlite.org/wal.html). PostgreSQL privileged append functions must follow the [function security rules](https://www.postgresql.org/docs/18/sql-createfunction.html), including fixed trusted search_path and PUBLIC privilege revocation.
