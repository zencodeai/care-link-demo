# Live IMP-03 browser checks

These tests require an actual protected runtime and separately issued provider accounts. Missing configuration fails; no live test silently skips. Use the [session002 G-03 guide](../../../doc/IMP/slices/IMP-03-protected-manual-service/sessions/002-runtime-completion/G-03-validation-guide.md) for exact commands and barrier ordering. Startup is in [the runtime runbook](../../../tools/imp03_runtime/README.md).

Copy `browser.example.json` outside the repository, mode0600, and replace every illustrative ID/credential with the exact issued synthetic account. The account UUIDs must match the initial runtime registry. All three accounts need real configured MFA for the fresh-recovery demonstration. The provider realm/client and four private cookie hostnames are independently provisioned inputs. Default browser certificate verification remains enabled. A local temporary-CA run using `ignoreHTTPSErrors: true` must record that exception; it does not qualify browser CA trust.

`normal` drives real provider sign-in, current role checks and UI conversation creation. Protected API requests and controlled real EventSource endpoints then exercise queue acceptance versus connection, both ACKs, attributed messaging, disconnect, takeover/old-owner denial, actual committed rotation with dropped HTTP acknowledgement, same-key reconciliation and an exact fresh-provider recovery ceremony. It does not constitute a complete UI/keyboard/screen-reader/EN-FR human review.

Each dependency phase first signs in and establishes successful protected service, writes `barrier-ready.json`, then waits for the matching operator barrier acknowledgement. Only actual subsequent HTTP denials pass. Use a fresh output directory for every invocation; barrier files use exclusive creation and unique nonces to reject stale receipts. Dependency pause must happen **after** readiness. Resume the exact paused process in operator cleanup. The fence phase is restriction-only and deliberately has no reset command.

Before readiness the browser obtains an exact-target CSRF proof and keeps it only in memory. After the fault it consumes that proof once to send the actual mutation POST without another CSRF-bootstrap dependency. The test independently observes that exact POST and records token-free method/path/status metadata. A bootstrap failure cannot stand in for mutation denial. The mocked-fetch regression in `tests/contract/imp03-barrier.test.ts` checks this harness behavior only; deployed denial and absence of prohibited durable effects still require live evidence.

The surviving `/private-help` check addresses the existing independently served help UI shell, exposed by `tools.imp02_application.browser.add_client(..., help_surface=True)`. It does not establish IMP-03 authenticated help/account integration or a service connection. `/fallback` checks the independent static content endpoint.

Traces, screenshots and video are disabled. Authorization navigation failures are sanitized, response assertions suppress bodies, and observations contain named outcomes plus token-free barrier request method/path/status metadata. Credentials, cookies and continuation tokens remain in the private input/browser memory. Keep Playwright JSON results private too; neither these checks nor a signature supplies human G-03 acceptance.
