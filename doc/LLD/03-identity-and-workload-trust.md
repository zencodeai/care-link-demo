# Human identity, continuation and workload trust

## OIDC login and assurance

Use server-mediated authorization code + PKCE S256 with fixed issuer/client/redirect URI and MFA for workforce/privileged access. Login intent stores hash of a cryptographically random state, nonce, PKCE verifier encrypted at rest, intended role/session, purpose, exact callback, browser-binding nonce, created/expiry (proposed 5 minutes) and state `{pending,redeeming,completed,failed,uncertain}`. It is single-use under an identity DB row lock. Do not accept unsolicited callbacks, caller redirect URLs or role upgrades from claims alone.

Callback validates state and browser binding before token exchange, then verifies token signature with allowlisted asymmetric algorithms and provider keys from pinned discovery/JWKS origins; reject `none`, unknown issuer, token-supplied jku/x5u and algorithm/key-type confusion. Verify exact iss, aud including client, azp as required for multiple audiences, nonce, exp/nbf/iat, subject, intended flow and required auth_time/acr/amr. Bound JWKS cache age and single-flight unknown-kid refresh; failed refresh cannot validate unknown keys. Validate access tokens separately for the resource audience/type; ID token is not an API bearer. No unsigned/decode-only claim path. Persist completion and rotate BFF cookie ID only after validation. These checks follow [OIDC Core](https://openid.net/specs/openid-connect-core-1_0-errata2.html); provider behavior is still tested against pinned versions.

Exchange timeout after provider code consumption makes intent `uncertain`. Never redeem a code concurrently or assume timeout means unused code. Clear local pending credentials, revoke any identified abandoned provider session where supported, and start a fresh login intent. A callback replay can return safe completed-login status to the same browser binding but cannot reissue credentials to another browser. No role dropdown, IP, caller ID or fingerprint links access principals to personas.

Local entitlements map `(issuer,subject)` to account UUID and separately granted role/purpose. OIDC group strings do not create local reviewer/worker/subject rights. Session assurance: AL0 continuation possession, AL1 explicit account/possession proof, AL2 recent reauthentication, AL3 fresh MFA step-up plus five-minute cooling-off for export/delete/identity-link. AL2/AL3 freshness is five minutes, privileged idle timeout 15 minutes. Since cooling-off consumes that window, AL3 execution requires a second fresh MFA reauthentication after cooling; it never relies on expired initial proof. An AL label alone is insufficient: record verified factor method, authentication time, purpose and ceremony ID. Workforce privilege requires separately provisioned entitlement and MFA. Per-operation requirements remain REQ identity.assurance.

## Current identity and revocation ordering

Every protected operation obtains a fresh identity-service validation response (no positive authorization cache), checks local account/role/credential guards at the final domain boundary, and binds both evidence and revisions. Provider introspection/status and local business commit are separate systems; a provider change after validation is an in-flight race, not an atomically recalled request. Locally requested revoke/disable is a journalled restrictive control and takes effect at the control barrier before acknowledgement; it invalidates browser sessions, delegation, streams, task leases and queued effects. Externally initiated provider revocation is observed through validated signals and fresh provider checks; record provider-event, received and local-fence times separately. Do not claim instantaneous upstream revocation. If fresh provider/account authority cannot be established, deny private operations. This limitation is part of identity integration acceptance.

Signed local identity signals use fixed issuer/audience, jti, subject, event type, event time, source sequence, previous-event digest and local receive time. Validate signature, issuer/audience/subject mappings, age ≤60 seconds and skew ≤5 seconds. Unique `(issuer,jti)` deduplicates; reused jti with other digest quarantines issuer. Source sequence and previous-event digest are scoped to (issuer,subject); issuer+jti remains globally deduplicated. Lower sequence/replay cannot roll back state. Gaps block affected authority until fresh snapshot reconciliation; ACK only durable accepted sequence. Expired signals trigger authoritative recovery, never positive rights. Local custom identity/control events are not SSF/CAEP conformance; provider-compatible SSF/CAEP can be adopted only after interoperability tests.

## Explicit continuation and lost replacement

Application continuation state belongs to the business data gateway, separate from provider login sessions. Continuation token is 256 random bits base64url with digest-only storage keyed by family, access principal, business session, channel, expires_at (10 minutes), generation and consumed_at. It carries AL0 only; issued participant login remains required by the closed perimeter. Identity service supplies fresh action-bound account proof; gateway rotation transaction locks family/session guard, checks current account/own-session rights and expiry, consumes old generation, stores replacement digest and canonical operation/audit. Raw replacement is returned once over private TLS and never logged. It cannot prove PID relationship or upgrade assurance.

If rotation committed but response was lost, same-key replay returns `replacement_unavailable` and operation status, never attempts to reconstruct a token from its hash or accepts the spent token as fresh authority. Recovery is explicit: authenticate the same access principal via a fresh AL1 ceremony bound to exact session/family and recovery intent, confirm own-session access, then revoke the old family and issue a new one under lock. Expired/revoked/stolen bearer alone cannot recover it. Recovery failure preserves business state, not access. A different principal or metadata-only proof fails. Lost recovery response repeats the same fresh-proof process; no automatic token escrow is introduced.

## Workload identity and proxy enforcement

DEC-01/B is the selected family; SPIFFE X.509-SVIDs, SPIRE attestation and Envoy proxies are the recommended product binding subject to host proof and explicit version pins. Give each admitted service a distinct `spiffe://care-link.demo/<environment>/<service>` identity. Attestation binds namespace, service account and admitted workload/image lineage; host bridge/help/journal need separately verified host attestation. Never derive identity solely from source IP, pod label or a shared static certificate. [SPIFFE Workload API](https://spiffe.io/docs/latest/spiffe-specs/spiffe_workload_api/) defines credential/trust updates; it does not itself supply business authorization or immediate session revocation.

Proxy validates trust domain, chain, SAN identity, validity, peer allowlist and method/path. Application listeners bind Unix socket/loopback reachable only by local proxy; inbound forwarded identity is accepted only through that protected socket, never public headers. CNI/host firewall blocks direct pod/host alternate ports and rejects IPv6 if untested. Runtime cannot mount workload issuer administration, Kubernetes API tokens, DB secrets or application delegation keys. Proxy bypass on a compromised pod is a deployment admission test, not assumed solved by a sidecar.

Proposed SVID lifetime is a release parameter, currently unresolved; choose only after rotation/outage tests. Rotate automatically before expiry; trust-bundle roll overlaps only verified roots. Compromise sets a central workload deny/fence generation before draining existing connections; every operation checks that generation, so a still-open valid TLS channel cannot keep permission. Certificate removal/expiry without connection fencing is insufficient. Issuer loss permits only already valid, currently authorized traffic within validity and current control checks; no new untrusted identities, manual bypass or expired certificates. Recovery requires human-authorized containment release and new credentials. Host/cluster root remains outside this isolation guarantee.

## Workload duties and delegated authority

VerifiedActor is discriminated human versus workload. A job/controller has an attested workload UUID/identity and exact signed duty artifact, purpose, allowed operations/resources, deadline and current fence, not an invented human role or login. Retention/checkpoint/expiry controllers may act under that bounded duty; discretionary release/promotion still requires actual human approval. Jobs executing prior actor intent retain originating human/task references and recheck current owner/consent/review, without impersonating an expired browser session. SignedDelegation carries either action-bound human identity evidence or workload-duty evidence and is method/path/body/audience/nonce bound. Unknown duties deny. No workload actor can enter a human reviewer slot.

The selected OIDC transport uses response_mode=query to the fixed GET callback, with exact state/code and optional issuer parameter; validate returned issuer if present against the configured issuer. SameSite=Lax supports this top-level return. No browser-supplied Idempotency-Key or CSRF header is expected on provider redirect: one-use bound intent/state supplies the protocol protection. A provider error response with matching state is handled as failed/cancelled intent with a safe message and no code exchange; error descriptions are never rendered as HTML. form_post is not silently enabled under this cookie policy. BFF and backend use the same pinned issuer identity despite internal routing differences. Callback query/code and credential headers are excluded from access logs.

Proposed login exchange timeout is 10 seconds within the 5-minute intent; business identity evidence and delegation expire within their original authorization deadline, at most 1000ms. JWKS cache maximum age is 300 seconds with single-flight bounded refresh; unknown/invalid keys fail closed. These are proposed local integration limits, not OIDC-prescribed values.

Local account/workload disable is a coordinated restriction: journal intent first fences the business authority, and the identity/help source must durably apply its own negative account/entitlement state under the same command ID before a completed global-disable acknowledgement. Cross-store partial success stays pending/blocked and reconciles idempotently; it is not an atomic multi-database commit. Help authorization continues using only its own current identity source, with its separately stated authorization boundary. No dependency on business PDP/audit/journal is introduced into each help request.
